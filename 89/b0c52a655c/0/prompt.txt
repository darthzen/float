# SPHEREx → All-Sky Equirectangular VR Starfield: Feasibility Report
*(as of 2026-07-24)*

## Bottom line up front
- **What exists TODAY at IRSA:** Level 2 *spectral images* (per-exposure multi-extension FITS), released weekly, currently the **QR2** ("Quick Release 2") processing. These are individual pointings, not a mosaic.
- **What does NOT yet exist (promised):** The official **102-band all-sky spectral data cubes / mosaics** (HEALPix, Galactic coords). Per the SPHEREx map-making paper these are scheduled for the **Year-1 data release ~November 2026** via an IRSA "public mosaic tool." So in July 2026 you would be building your own mosaic OR waiting ~4 months for the official one.
- **The pretty "all-sky maps" NASA already published** (May 2025 onward) are **visualizations only** — spatial resolution deliberately reduced by ~1000×, not science-grade downloadables.
- **Feasibility verdict:** Mosaicking raw L2 yourself is possible but heavy (~2.3 million exposures over the mission; hundreds of thousands already public). For a VR starfield the **sane path is to wait for / use the official HEALPix all-sky cubes and reproject them to equirectangular (CAR)** with `reproject`/`healpy`. That is a single-GPU, few-hours job rather than a mosaicking pipeline project.

## 1. SPHEREx public data products at IRSA (mid-2026)

**Release cadence &amp; status**
- **QR1**: weekly releases began **July 2025**. Now legacy (QR1 on AWS only through Jan 2026).
- **QR2**: weekly releases began **October 2025**, improved calibration, supersedes QR1. This is the current live product.
- **Latency:** data appears publicly **~60 days after observation**.
- First full all-sky *coverage* epoch was acquired early 2026 (survey runs May→Dec 2025 for pass 1). Four all-sky passes total over the 25-month mission (2 sky surveys/year).

**Level 2 Spectral Images (available now)**
- Format: **Multi-Extension FITS (MEF)**. **6 MEFs per sky pointing** (one per detector), **~70 MB each**, 6 extensions.
- Each detector image: **2040 × 2040 pixels, native ~6.15 arcsec/pixel** (≈ your 6.2"; note the PSF is oversampled internally at 0.615"/sub-pixel — don't confuse the two; the science pixel is 6.15").
- Extensions include: calibrated flux, per-pixel flags/status, variance map, zodiacal-light model, exposure-averaged PSF, and **spectral WCS** (which wavelength each pixel sampled — because of the Linear Variable Filters, wavelength varies across the array).
- Six bands 0.75–5.0 µm (Band1 0.75–1.09; Band2 1.10–1.62; Band3 1.63–2.41; Band4 2.42–3.82; Band5 3.83–4.41; Band6 4.42–5.00), R≈35–130. The 102 "colors" come from co-adding many exposures that sampled each sky position at different LVF wavelengths.
- Calibration products also public (gain, dark, PSF ~6 MB [101×101×121], dichroic, solid-angle maps, etc.).

**All-sky maps / data cubes (promised, not yet public)**
- Year-1 &amp; Year-2 releases will include **102 single-color full-sky mosaics** ("Data Cube" product) — spatially+spectrally interpolated all-sky maps at 102 wavelengths.
- Projection: **HEALPix in Galactic coordinates** for science; the coverage-monitoring maps use Mollweide at Nside=1024 (3.4' pixels). Science full-sky products use HEALPix representation, delivered via an IRSA "public mosaic tool."
- **Scheduled ~November 2026** (Year-1). As of July 2026: **not released yet.**

**Rough full-sky download size (build-your-own from L2)**
- Mission total ≈ **2.3 million exposures**; 14 billion spectra; ~1.4 trillion voxels *per* all-sky pass. At ~70 MB × 6 detectors per pointing, the full L2 corpus is on the order of **hundreds of TB**. Even one complete sky pass of L2 is tens of TB. This is the main argument against DIY mosaicking.

## 3. How popular all-sky renderings / colorizations are made

**NASA/JPL SPHEREx visualizations (SVS 31376, PIA26600)**
- Elliptical (Mollweide-style) all-sky projection; **resolution reduced ~1000×** from native.
- Two colorization schemes documented: (a) science/ISM view — 4 µm hot hydrogen → **blue**, 3.4 µm PAH dust → **red**; (b) stars/galaxies view — **short/medium/long wavelength → blue/green/red**. No public code, but the convention (short→blue, long→red) is the standard.

**Precedent pipelines you can copy**
- **Lupton et al. asinh RGB** (the canonical false-color method): asinh stretch preserves faint structure while not saturating bright cores — the de-facto standard for SDSS, unWISE, HiPS. (`astropy.visualization.make_lupton_rgb`.) Paper: astro-ph/0312483.
- **unWISE / WISE all-sky:** 2.75"/pix coadds at 3.4 &amp; 4.6 µm (W1/W2), Meisner/Lang coadd methodology; a well-documented 2-band → color precedent very close to your SPHEREx use case.
- **Gaia DR2 "Sky in Colour":** built with **HEALPix + healpy**; flux/density maps binned to HEALPix (up to Nside=8192 ≈ 0.18 arcmin²/pixel), then plane-projected; interactive via GAVS. Good reference for HEALPix→image color compositing.
- **HEALPix → equirectangular (CAR)** is a solved problem: `reproject_from_healpix(..., &lt;CAR WCS&gt;)`; healpy `projview`. This is exactly the last step you need for a VR equirect texture.

## 4. Effort estimate — single V100 pod, astropy skills

**Two realistic paths:**

**Path A — Wait for / use official HEALPix all-sky cubes (recommended).**
- Available ~Nov 2026. Download 102 HEALPix maps (Galactic), pick your band-to-RGB triplets, apply asinh/log stretch (Lupton), `reproject_from_healpix → CAR`, tile into equirect layers.
- Effort: **days**, not months. Trivially fits a single V100 (it's mostly I/O + reprojection, GPU barely needed except for compositing/upscaling). Multiple wavelength/depth layers = just choose different band groupings.

**Path B — Build your own mosaic from L2 now.**
- You'd query L2 via SIA2, handle each exposure's **per-pixel spectral WCS** (wavelength varies across array), regrid/bin onto a common HEALPix grid per wavelength channel, coadd with hit-count/variance tracking, mask zodiacal light. This replicates the mission's L2→L3 mapmaker.
- Effort: **weeks–months**; data volume tens–hundreds of TB; the wavelength-assignment/coaddition bookkeeping is the hard part, not the compute. Feasible on one V100 only if you restrict to a sky region or a few bands. Not recommended for a first all-sky VR texture.

**Coverage gaps / solar exclusion (important for early releases):**
- SPHEREx surveys in great circles roughly perpendicular to the Sun; there are **solar-exclusion / partial-coverage regions** and the ecliptic poles get very deep coverage (the two "deep fields"), while a full uniform all-sky pass only completes every ~6 months. Early QR data has **uneven depth and coverage holes** — a mid-2026 DIY mosaic would have visible gaps/seams. The official Year-1 cube is specifically the point at which full, gap-filled all-sky coverage is guaranteed. ## 5. Resolution ceiling (equirectangular full-sky, pixels wide)

Equirect width = 360° of sky / pixel scale; height = width/2.

| Survey | Pixel scale | Equirect width × height | Notes |
|---|---|---|---|
| **SPHEREx (native)** | 6.2″/pix | **≈209,000 × 104,500** (~21.8 Gpx/band) | 1,296,000″ ÷ 6.2. Per mono band; ×102 for full cube |
| WISE / unWISE coadds | 2.75″/pix | ≈471,000 × 236,000 (~111 Gpx) | Finer than SPHEREx — deeper 2-band imaging |
| Gaia DR2 sky image | ~1.5′ (90″)/pix effective | ≈14,400 × 7,200 | The *image* is coarse though astrometry is ~100 µas |

**Practical takeaways for VR:**
- A full-res SPHEREx equirect band is **~209k px wide (~21 gigapixels)** — far beyond a single GPU texture. You'll tile/mip it (e.g., 16k or 32k equirect for the base VR sphere, with higher-res tiles streamed).
- SPHEREx's spatial resolution (6.2″) is actually **coarser than unWISE (2.75″)** — SPHEREx's unique value is the **102 spectral channels**, not spatial sharpness. For a starfield, consider using unWISE/DSS for spatial crispness and SPHEREx for the spectral/false-color layers.
- Storage sanity check: one 16-bit mono band at native res ≈ **44 GB**; a 3-band 8-bit RGB equirect ≈ **65 GB** — so downsample aggressively for the VR base layer and keep native only for zoom tiles.

## Design decisions (with what I verified)

### 1. Data access: CDS hips2fits (path a) — chosen

Verified against the live docs at `https://alasky.cds.unistra.fr/hips-image-services/hips2fits` (mirror: `https://alaskybis.cds.unistra.fr/hips-image-services/hips2fits`):

- Parameters: `hips`, `width`, `height`, `projection` (CAR **is** listed as supported), `coordsys` (`icrs`|`galactic`), `ra`/`dec`/`fov` OR a `wcs` JSON dict of header key-values, `format` (`fits` default | `png` | `jpg`), `min_cut`/`max_cut`/`stretch`/`cmap` (only relevant for png/jpg), `rotation_angle`, `inverse_longitude`.
- **Hard cap verified: width × height ≤ 50 Mpx.** 12288×6144 = 75.5 Mpx, so the full-res pull must be striped. 12288×1536 = 18.9 Mpx per strip → 4 latitude strips per band, each well under the cap (and small enough to dodge server timeouts).
- unWISE HiPS IDs verified via MocServer (`alasky.cds.unistra.fr/MocServer/query?ID=*unWISE*`): **`CDS/P/unWISE/W1`**, **`CDS/P/unWISE/W2`**, and prebuilt color **`CDS/P/unWISE/color-W2-W1W2-W1`** (the ID itself confirms the R=W2, G=(W1+W2)/2, B=W1 convention).
- `CDS/P/unWISE/W1` record verified: `hips_tile_format = jpeg fits` — **FITS tiles exist**, so `format=fits` returns real float values per band and we do our own stretch. `hips_order = 8`; copyright "CNRS/Universite de Strasbourg", license ODbL-1.0, "IPAC/NASA - D. Lang for the reprocessing".
- The HiPS pyramid is precomputed at every order, so the server does the 38× downsample (2.75″ native → ~105″/px at 12288 wide) by picking the right order — the supersampling problem is solved server-side for free.

**Rejected (b) raw unwise.me coadd tiles:** 18,240 tiles × 2 bands, hundreds of GB, plus our own tangent-plane→CAR mosaicking and inter-tile background matching, to feed a 75 Mpx product. Pure overkill.
**Rejected (c) direct HiPS tile download + reproject:** HiPS tiles are HPX-projected image tiles, not `reproject_from_healpix`-consumable HEALPix maps; would require astropy + astropy-healpix + custom code to reimplement what hips2fits already does server-side.

### 2. Colorization: Lang/Legacy-Surveys convention — chosen

Verified the exact reference implementation, `_unwise_to_rgb` in `legacysurvey/legacypipe` `py/legacypipe/coadds.py`:

```python
scale1 = scale2 = 50.;  mn, mx = -1., 100.;  arcsinh = 1.
img1 = w1/scale1; img2 = w2/scale2
nlmap(x) = arcsinh(x*arcsinh)/sqrt(arcsinh)
mean = (img1+img2)/2; I = nlmap(mean); img_i = I*img_i/mean   # color-preserving asinh
normalize by (nlmap(mn), nlmap(mx));  B = img1(W1), R = img2(W2), G = (R+B)/2
```

This is *the* documented unWISE convention (matches the CDS color HiPS), is native to 2 bands, and its color-preserving asinh is exactly what tames the galactic bulge. Lupton `make_lupton_rgb` is rejected: needs astropy, and needs a synthetic green anyway — Lang's formulation *is* a Lupton-style asinh with the synthetic green built in. Keep `scale_per_band`, `mn`, `mx`, `arcsinh`, and the 3×N band→channel matrix as named tunables so SPHEREx's N=102 drops in later (default matrix for unWISE: `R=[0,1], G=[.5,.5], B=[1,0]`).

Caveat (unverified): Lang's defaults assume native unWISE coadd flux units; the CDS FITS tiles *should* preserve them, but ship a `--auto-cut` percentile fallback in case the served values are rescaled.

### 3. Coordinate frame / orientation

- Verified in `CREDITS.md`: the base plate `starmap_2020_8k.exr` is the **celestial (equatorial)** SVS variant (galactic `_gal.exr` variants exist but weren't used). Scenes are standalone skies, though — nothing in the app requires cross-scene frame agreement.
- Verified in `SpatialImageEnvironment.swift` (`makeSphere`, line ~233): the sphere gets a −90° Y rotation so **equirect center column (u=0.5) faces −Z at launch** — "lon 0 = forward".
- **Recommendation: galactic frame, galactic center at image center.** For an IR dust map this is the canonical presentation (WISE/Planck): the Milky Way band runs horizontally around the viewer like a glowing horizon, and the bulge — the best part of the IR sky — is straight ahead at launch. Use `coordsys=galactic` / `GLON-CAR`/`GLAT-CAR` with GC at CRVAL.
- **Mirror-parity risk (must verify empirically at preview):** an inside-of-sphere texture must be east-left "sky seen from within". Toggle is the `CDELT1` sign (or `inverse_longitude`). Verification anchor: in the preview, the Large and Small Magellanic Clouds must sit on the correct side of the bulge relative to any planetarium view (e.g. compare against the `spatial_deep_star_map` thumbnail, accounting for the frame difference, or Aladin Lite in galactic mode).

### 4. Dependencies: none new

Verified: pipeline Python is pyenv 3.14.5 with only `numpy 2.5.0` + `PIL 12.3.0` (astropy/reproject/healpy/scipy/tifffile all missing). hips2fits FITS output is a single primary HDU, float, big-endian — a ~35-line reader (2880-byte header blocks, parse `NAXIS1/2`, `BITPIX` −32/−64, `&gt;f4`/`&gt;f8` via numpy) suffices. Strong repo precedent: `backdrop_tool.py` already hand-parses Radiance RGBE for exactly this reason.

### 5. Background / zero point

For a visual product: per-band global percentile subtraction (default: subtract the ~30th percentile, clamp negatives to 0) applied before the Lang stretch. unWISE full-depth coadds have low-level moon-glow/scan stripes in W2; at 105″/px most average away, and asinh compression hides the rest. Expose `--bg-pct` as a tunable; do **not** attempt spatially varying background fitting unless the preview shows visible banding (note it as the escalation path).

## Implementation steps

### Step 1 — `scripts/fetch_unwise.py` (fetch stage, `fetch_potm.py` style)

Output dir `Float/Resources/Textures/_raw/unwise/fits/`. Two subcommands:

- `preview`: per band, one request — `hips=CDS/P/unWISE/W1|W2, width=4096, height=2048, projection=CAR, coordsys=galactic, ra/dec at GC (0,0 galactic — verify how ra/dec are interpreted under coordsys=galactic; if ambiguous, use the wcs form here too), fov=360, format=fits` → `W1_preview.fits`, `W2_preview.fits` (~33.5 MB each).
- `fetch`: per band, 4 strips of 12288×1536 via the `wcs` JSON param: `CTYPE1/2 = GLON-CAR/GLAT-CAR`, `CDELT = ∓360/12288 = ∓0.029296875`, `CRVAL = (0,0)`, `CRPIX1 = 6144.5`, `CRPIX2 = 3072.5 − strip_row0` (CAR requires CRVAL2=0; strips select the lat band purely via CRPIX2). ~75.5 MB/strip, 8 strips total.
- Resumable like fetch_potm: skip strips already on disk at expected size; sequential requests with retry/backoff; fall back to the `alaskybis` mirror on failure; same UA convention (`Mozilla/5.0 (Float unWISE fetcher; rick@theashfords.org)`).

### Step 2 — `upscale/allsky_rgb.py` (source-agnostic band→RGB compose)

- Minimal FITS reader (as above); assemble strips bottom-to-top per band → float array per band.
- Stage contract (SPHEREx-ready): `compose(bands: list[np.ndarray], matrix: 3×N, scales: N, mn, mx, arcsinh, bg_pct) -&gt; uint8 RGB`; unWISE defaults are just one named config dict.
- Wrap-seam sanity check built in: assert column 0 vs column −1 mean abs diff is small; also warn on NaN count (nan_to_num).
- Outputs: `_raw/unwise/unwise_w1w2_equirectangular.tif` (8-bit sRGB, deflate-compressed TIFF — matches the SPHEREx `_raw/spherex/*.tif` precedent; `load_linear` handles 8-bit sRGB TIFF via PIL) + a 2048-wide preview JPG into `upscale/deepsky_prev/` for eyeballing.
- **Preview the downstream look:** `process_backdrops.mono_hires` runs the tif through `load_linear`→`tonemap` (Reinhard), which darkens mids. Add a `--simulate-tonemap` preview mode that shows the post-Reinhard result; if too dark, the MANIFEST `hdr_exposure` slot (passed to `tonemap`) is the sanctioned knob — no special-casing needed.

### Step 3 — Low-res preview gate (do FIRST, before the 600 MB pull)

`fetch_unwise.py preview` → `allsky_rgb.py --preview` (4096×2048) → Rick eyeballs: (a) does IR-only sky read as a starfield or as a dust smear? (b) bulge blown out? (c) mirror parity correct (Magellanic Clouds check)? (d) seam clean? Only then run the full fetch. Total cost of the gate: ~10 minutes, ~70 MB.

## Risks

- **50 Mpx cap** (verified) — handled by striping; **rate limits undocumented** — sequential + retry + alaskybis mirror.
- **`wcs` JSON with GLON-CAR unverified** — I could not test a live request; implementer should validate with one cheap 512×256 strip first. If galactic CTYPEs misbehave, fall back to equatorial `RA---CAR` full-sky and roll/flip columns in numpy (a CAR frame rotation about the poles is a pixel roll; a full galactic↔equatorial rotation is not — so prefer fixing the request, not post-hoc numpy).
- **Galactic plane saturation** — Lang asinh is designed for this data; `mn/mx/scale` tunables + preview gate.
- **IR sky may read dust-heavy, not starry** — that's the point of the Step-3 gate; if rejected, the scripts still stand as the SPHEREx dry run.
- **Flux-unit assumption behind Lang defaults** — `--auto-cut` percentile fallback.
- **iCloud disk** — ~0.9 GB lands under `_raw/unwise/`; consider the off-repo archive note pattern used for `_raw/potm`.

## Estimates

- Preview gate: ~70 MB, ~10 min including eyeball.
- Full fetch: ~604 MB FITS (8 strips × 75.5 MB), 30–90 min wall (server-render bound).
